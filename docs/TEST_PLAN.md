# Test Plan

Release candidates must cover:

- Argon2id known-answer vectors using fixed passphrase/salt/parameters.
- Hostile/untrusted KDF metadata bounds before Argon2 work: salts shorter than 16 or longer than 64 bytes, memory outside 16–512 MiB, iterations outside 1–10, and parallelism outside 1–16 must be rejected without honoring the excessive resource request.
- Backup headers must validate format version, salt length, KDF resource bounds, and chunk size before any Argon2 derivation. Unsupported/malformed metadata must fail as invalid backup data.
- Backup export destinations must never resolve to the active vault database, SQLite WAL/SHM/recovery files, or the encrypted attachment directory. Export staging must use a collision-resistant sibling path opened with `CreateNew`.
- Consistent SQLite snapshot destinations must never resolve to the active database, WAL/SHM, or `.previous...` recovery naming family. A pre-existing destination must not be overwritten, and a newly created partial snapshot must be cleaned best-effort if backup creation fails.
- Backup ZIP restore must reject duplicate normalized entry paths and encrypted attachment entries outside the actual CipherNest attachment-container size envelope, in addition to existing total archive/count/path bounds.
- Restore rollback must use an uncancelled recovery token after active-state mutation begins; caller cancellation must not cancel the rollback database replacement. Attachment rollback directories must be collision-resistant.
- AES-GCM round-trip, nonce-size validation, associated-data binding, record tamper rejection, and wrong-key rejection.
- Wrong master passphrase, recovery-key behavior, secondary biometric-wrapper behavior, and per-item re-authentication rules.
- Vault headers must accept only explicitly supported versions and reject future/unknown versions before key unwrap. Header metadata must remain within the 64 KiB UTF-8 storage budget before deserialization.
- Master-passphrase changes must end the current security session, lock the vault, clear the remembered master-authentication timestamp, and require the new master passphrase before biometric convenience unlock can resume.
- Failed interactive unlocks must follow the bounded backoff schedule, reset after success, and never be represented as protection against offline attacks on a copied database.
- In-flight key-using work must use zeroing private key leases linked to the current unlock session. Locking must cancel those leases so plaintext attachment export and other cancellable vault I/O cannot continue after the security session ends.
- Master/recovery unlock, secondary unlock, public lock, and full-vault deletion must share the serialized service transition gate. Race/stress tests must verify a late-finishing unlock cannot publish a session after an already-requested lock.
- Full-vault deletion must keep a live authorization key lease while waiting for the transition gate. If another lock/unlock invalidates that session before deletion acquires the gate, the destructive action must be cancelled rather than proceed on stale re-authentication.
- Backup corruption, wrong backup passphrase, authenticated attachment restore, and restore atomicity/preservation of the active vault after failed restore.
- Replacement databases must pass SQLite `quick_check`, exact supported schema-version validation, required table/column shape validation, required vault-header presence/size validation, canonical item-ID validation, and encrypted-record count/per-record/aggregate size budgets before active database/WAL mutation. Invalid replacements must leave the active vault intact.
- SQLite replacement must stage the database, WAL, and SHM as a unique recovery file set. Rollback must restore only components that were actually staged so an unstaged sidecar is not deleted during partial recovery.
- Schema creation, migration idempotence, ordered migration history, required table/column shape validation, rejection of forged current-version history with missing schema objects, and rejection of unsupported future schemas.
- Migration rollback and database replacement recovery must preserve the original failure rather than masking it with a secondary rollback exception.
- Stored encrypted records must enforce the shared budgets on both reads and writes: at most 100,000 items, 24 MiB per stored envelope, and 256 MiB aggregate envelope bytes. SQLite length/count checks must run before BLOB materialization.
- Serialized/decrypted item JSON must stay within 16 MiB and the application-level combined item text budget must stay within 2,000,000 characters; custom-store implementations must still be bounded by `VaultService`.
- Stored item IDs must be canonical lower-case GUID `D` strings, non-empty, and must continue to match the decrypted authenticated item ID.
- Multi-megabyte encrypted attachment streaming round trips across multiple 256 KiB chunks, truncation/tamper rejection, and 100 MB bounds.
- Attachment encryption must zero reusable plaintext buffers, use collision-resistant `CreateNew` staging, and fail closed rather than overwrite an existing encrypted attachment container.
- Opaque encrypted attachment storage names must be GUID-based `.cna` names without path separators; malformed names must be rejected before filesystem access.
- Attachment metadata must enforce non-empty/size-bounded names and media types, 100 MB plaintext bounds, non-empty identifiers/storage names, and per-item uniqueness of attachment IDs and storage names.
- Safe text-attachment preview type/size/UTF-8 limits and no-temp-file behavior where practical to automate.
- CRUD/search/filter/sort/audit while unlocked and denial while locked.
- Decrypted record payloads must match their authenticated database row ID and pass item metadata validation before leaving the infrastructure boundary; plaintext record buffers must be zeroed on all exits.
- Item validation must reject runtime-null collections/strings, empty identifiers, unknown item types, oversized fields, invalid custom fields, invalid attachment metadata, duplicate attachment identifiers/storage names, and excessive aggregate text without throwing `NullReferenceException`.
- Large-vault UI behavior must page rendered results incrementally while preserving local search/filter/sort result counts.
- Weak, reused, exact-duplicate, missing-title, and overdue-review audit findings.
- Safe secure-note Markdown subset, checklist editing, HTML neutralization, fenced-code behavior, and shared 200,000-character/5,000-line limits across editor parsing and every stored/imported item save path.
- Password generator selected-group guarantees, ambiguous-character exclusion, 256-entry passphrase-list invariants, requested word counts, passphrase lower bounds, and cleanup of temporary generated password/passphrase arrays after the returned managed string is created.
- CSV valid quoting, duplicate/empty headers, unterminated quotes, characters after closing quotes, excessive columns/fields/rows, and malformed-parser corpus coverage. The maximum-column rule must also apply to the final field at newline/EOF, not only delimiter-terminated fields.
- CSV parser hot paths must not allocate a new one-character buffer for every input character.
- Plaintext export confirmation phrase, master-passphrase re-authentication, explicit warning, temporary-cache cleanup path, and no attachment inclusion.
- Clipboard username/password/custom-secret copy must remain explicit. Delayed cleanup must keep only a fixed-size fingerprint, not the plaintext secret; comparison must be fixed-time; caller cancellation after a successful copy must not silently disable the security timer; manual/background/timeout cleanup must preserve unrelated newer clipboard content.
- Manual lock, lock on background, lock after inactivity/resume, clock-rollback fail-closed behavior, and lifecycle error handling. Fail-closed cleanup must separately contain/report secondary lock and clipboard exceptions instead of allowing a cleanup error to escape an `async void` lifecycle callback.
- Bound credential fields must be cleared before long-running/authenticated work wherever practical: Unlock, Onboarding, Transfer plaintext export, Trash destructive re-authentication, per-item re-authentication, Settings biometric configuration, backup/restore, master-passphrase rotation, and full-vault deletion. Managed-memory limitations remain documented.
- Settings persistence must round-trip the complete current `AppPreferences` model, normalize invalid enum/numeric values on load/save, restore at least one password character group when password mode has none, fall back safely on malformed/unreadable non-secret settings files, use collision-resistant sibling staging, and clean staging files where possible without swallowing cancellation.
- Storage measurement/cache cleanup must materialize directory enumerations inside guarded blocks and must not recurse through reparse-point directories.
- Trash retention cutoffs must be deterministic and bounded. Automatic configured-retention cleanup must run during routine vault maintenance, while manual permanent deletion/empty-trash actions require current master-passphrase re-authentication and explicit confirmation.
- Permanent item deletion must remove the database record before best-effort encrypted attachment cleanup so a failed database delete cannot leave a surviving item that points to already-removed files.
- Android biometric source must not depend on a preflight API newer than the advertised API-28 `BiometricPrompt` baseline; real devices must cover enrollment, absence, lockout, cancellation, hardware availability, and fallback behavior.
- iOS/Mac Catalyst biometric cancellation must invalidate the native context when the request token is cancelled; real Apple targets still require enrollment/device tests.
- Screenshot-protection behavior where supported, with explicit fallback verification elsewhere.
- Theme/accessibility checks: larger-interface setting, OS large text, keyboard focus, screen-reader labels/live regions, contrast, touch target size, responsive narrow/desktop layouts, and reduced-motion behavior.
- English resource fallback, saved System/English language preference, and layout resilience when future localized strings expand.
- Privacy-safe diagnostics: operation identifiers may be logged, while exception message, stack, vault fields, passphrases, keys, paths, and decrypted attachments are absent. Settings backup/restore/delete/storage/biometric failures, plaintext transfer file failures, item open/attachment failures, capability probes, external-link failures, lifecycle cleanup, and temporary plaintext cleanup must use fixed UI text plus the privacy-safe reporter rather than directly rendering raw exception messages.
- Temporary decrypted attachment export paths must use a collision-resistant name and cleanup failure must be visible without leaking the path.
- Project-support metadata consistency: `AppConstants.BuyMeACoffeeUrl`, About, README, SUPPORT, and `.github/FUNDING.yml` must resolve to `https://buymeacoffee.com/sanskarIN`; About public URLs/emails should continue to bind from shared constants rather than duplicate values.
- Funding CTA build gating: default app builds expose the optional support surface; builds with `CipherNestEnableFundingLink=false` must compile the disable symbol and hide the in-app support frame/metadata while leaving repository funding metadata unchanged.
- Branding checks must verify the original vector mark, splash wordmark, `Made by the Sanskar` credit, monochrome source, and dark-surface logo source without placing branding over user content.
- Main CI must retain core restore/build/test/format gates plus Windows default/funding-disabled compilation, Android compilation, and iOS/Mac Catalyst compilation. CI/CodeQL/dependency review must retain explicit timeouts and superseded-run cancellation.
- CodeQL must analyze the MAUI application path in addition to non-MAUI/core code.
- Android/Windows smoke tests plus iOS/MacCatalyst builds and smoke tests on an appropriate Apple host/device or simulator.
- Dependency vulnerability scanning, dependency review, CodeQL, and secret scanning.

## Current automated source coverage

The repository includes unit/integration tests for cryptographic behavior, Argon2id known-answer and hostile-resource bounds, backup-header/path/rollback resource behavior, protected snapshot destinations, vault lifecycle, backup/restore corruption and wrong-passphrase preservation, passphrase rotation, secondary unlock wrappers, vault-header compatibility/size limits, generator behavior, secure-note parsing/limits, local audit findings, settings normalization/persistence/staging cleanup, schema migration/forged-history/replacement preservation, malformed CSV parsing/final-field column limits, multi-megabyte attachment streaming, attachment storage-name/staging policy, item/attachment/aggregate-text validation, encrypted-record storage bounds, attachment tamper/truncation rejection, and lock-cancelled plaintext attachment export.

Pure unit-test policies cover session lock timing/background behavior, clock rollback, clipboard clear-delay bounds/fingerprint matching, trash-retention cutoffs, settings normalization, backup-header/path bounds, attachment storage names, vault-item bounds, and failed-unlock exponential backoff. UI/source tests cover core routes, semantic metadata, localization structure, responsive/incremental vault layout, explicit clipboard actions, fingerprint-only delayed clipboard cleanup, sensitive-page cleanup hooks, shortened credential binding lifetime, master-passphrase session reset, guarded trash deletion, contained lifecycle fallback, privacy-safe sensitive error surfaces, no legacy `.DisplayAlert(` calls, privacy-safe unlock/external-link diagnostics, attachment buffer/staging cleanup, backup restore hardening, protected snapshot destinations, vault-header/deletion ordering, replacement validation/component-aware rollback ordering, encrypted-record resource checks, cancellable zeroing key leases, serialized vault session transitions, live-session full-vault-deletion authorization, decrypted-record validation, storage enumeration guarding, generator temporary-array cleanup, legal surfaces, branding-source requirements, project-support metadata consistency, centralized About metadata bindings, the store-toggleable funding CTA, cross-platform CI jobs, CodeQL MAUI coverage, dependency review, and verification-script presence.

Configured automation now includes core tests/formatting, Windows default/funding-disabled app compilation, Android app compilation, iOS/Mac Catalyst app compilation, CodeQL application analysis, and pull-request dependency review. See `docs/verification/CI_GATES.md`. These configured gates are not represented as passing until GitHub or the appropriate local release environment executes them for the exact candidate commit.

Device-specific biometric, screenshot, clipboard API behavior, lifecycle callbacks, session-transition race timing, share-sheet/cache deletion, in-memory preview presentation, browser/launcher behavior, accessibility, localization rendering, store-policy interpretation, signing, and packaging behavior still require target-platform execution; source presence is not treated as proof that a platform guarantee works.

A release is blocked by failing tests/builds/formatting/analyzers, unresolved high-severity dependency findings, known secret/path leakage, a broken migration/restore compatibility path, an unbounded untrusted resource parameter, stale destructive authorization surviving a session transition, malformed stored metadata escaping validation, or an unreviewed cryptographic format change.
